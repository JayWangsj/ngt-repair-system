# 意大利手机维修店管理系统 MVP 技术方案

## 1. 方案目标与边界

本方案用于支撑 MVP 的完整闭环：快速登记工单、按规则建议报价、跟踪维修状态、记录收款与交付，并让店主在首页掌握当日重点。

首版采用单店、多员工的响应式 Web 应用，不建设原生 App、微服务、库存、电子发票、自动消息或多门店能力。系统应优先保证业务数据可追溯、操作简单、部署和维护成本低。

## 2. 总体架构

采用 TypeScript 单体 Web 架构：浏览器访问 Next.js 应用；应用同时提供页面渲染、业务接口和鉴权；所有业务数据存于 PostgreSQL；照片等二进制附件存于 S3 兼容对象存储。

```text
店主 / 店员浏览器
        │ HTTPS
        ▼
Next.js + TypeScript 应用
  ├─ 页面与交互（React）
  ├─ 业务接口 / 鉴权 / 权限校验
  ├─ 报价匹配、状态流转、经营汇总
  └─ Prisma ORM
        │
        ▼
PostgreSQL ────────── S3 兼容对象存储（后续照片/签字）
```

此阶段不拆分独立前端、后端或微服务。业务规模和接口边界都还较小，单体可减少部署组件和跨服务一致性问题；未来若增加线上预约、移动端或第三方集成，可在稳定的业务模块边界上逐步抽出 API 服务。

## 3. 推荐技术栈

| 层次 | 选型 | 作用与理由 |
| --- | --- | --- |
| 开发语言 | TypeScript | 前后端共享类型，降低工单、报价和付款字段不一致的风险。 |
| Web 框架 | Next.js（App Router） | 统一交付响应式页面和服务端接口，适合 CRUD 为主的内部管理系统。 |
| UI | Tailwind CSS + shadcn/ui | 快速构建清晰、可复用且适合表单密集场景的界面。 |
| 表单与校验 | React Hook Form + Zod | 在客户端和服务端共享输入规则，降低漏填、金额格式错误等问题。 |
| 数据库 | PostgreSQL | 适合客户、设备、工单、付款和日志之间的关联、约束与统计查询。 |
| 数据访问 | Prisma ORM + 迁移 | 使用受版本控制的迁移管理数据结构，并提供类型安全访问。 |
| 鉴权 | Auth.js | 支持会话管理，并作为店主/店员角色控制的基础。 |
| 文件存储 | S3 兼容对象存储 | 预留设备照片、签字和收据，不把大文件直接存入主库。 |
| 测试 | Vitest + Playwright | 前者验证领域规则，后者验证登记至交付的关键流程。 |
| 交付运维 | Docker + CI | 保持本地、测试和生产环境的一致性，并在合并前自动验证。 |

## 4. 业务模块与职责

| 模块 | MVP 职责 |
| --- | --- |
| 身份与人员 | 登录、会话、店主与店员角色；记录操作人。 |
| 客户与设备 | 以电话号码检索客户；维护一对多设备档案和工单历史。 |
| 工单 | 创建、编辑、查询、状态流转、预计交付、交付记录及备注。 |
| 报价 | 维护规则；匹配建议价；保存最终价与调价原因。 |
| 收款 | 记录每笔订金/尾款、金额、支付方式和时间；计算未结款。 |
| 看板与概览 | 输出各状态数量、待取机、逾期、未结款及当日收款。 |
| 审计日志 | 记录状态变更、报价修改、付款和交付等关键操作。 |

## 5. 数据设计原则

### 5.1 核心实体

- `User`：员工身份、显示名、角色、启用状态。
- `Customer`：姓名、电话、最小必要联系信息、隐私同意时间。
- `Device`：归属客户、品牌、系列、型号、可选 IMEI、外观和附件描述。
- `WorkOrder`：工单编号、设备、当前状态、故障描述、预计交付、交付信息、备注。
- `WorkOrderItem`：工单中的维修项目，保存匹配到的规则、建议价、最终价、调价原因和预计工时。
- `PriceRule`：品牌/系列/型号、维修项目、建议价、可选成本价、启用状态及备注。
- `Payment`：工单、金额、支付方式、收款时间、收款人及付款性质（订金/尾款/其他）。
- `StatusHistory`：工单状态变化前后值、时间、操作人和可选备注。
- `AuditLog`：关键变更的动作、主体、操作者、时间和必要的结构化上下文。

金额使用 PostgreSQL `numeric`，应用层使用整数分或专用十进制类型计算，绝不使用 JavaScript 浮点数累计金额。所有时间用带时区的时间戳保存，界面按 `Europe/Rome` 展示；日期展示采用意大利习惯，金额格式采用 EUR。

### 5.2 不可变业务快照

报价规则是可编辑的，但工单中的 `WorkOrderItem` 必须保存当时的建议价、最终价、匹配层级和调价原因。付款记录必须追加而不是覆盖。这样即使之后修改报价表或员工资料，历史工单仍能完整解释“当时为何这样报价、已收了多少款”。

## 6. 关键业务规则

### 6.1 报价匹配

针对“设备 + 维修项目”按以下顺序查找已启用规则：

1. 精确品牌、型号和项目。
2. 品牌、系列和项目。
3. 通用项目规则。

命中时将规则的建议价写入工单项目快照；未命中时允许手动输入。手动输入可由店主或具备明确授权的员工另存为新规则。多维修项目的工单以各项目最终报价合计为应收金额。

### 6.2 状态与交付

状态限定为：`已接收`、`检测中`、`等待客户确认`、`维修中`、`待取机`、`已完成`、`已取消`。每次修改必须在同一数据库事务内更新当前状态并新增 `StatusHistory`。交付操作需要记录取机时间、取机人，并将工单改为 `已完成`；若仍有未结余额，应在界面明确提示并要求有权限的人员确认。

### 6.3 权限与审计

店主可管理报价规则、员工、所有工单与经营概览。店员可创建、编辑被授权的日常业务数据、更新状态和记录付款，但不能管理员工或修改系统级设置。关键写操作均在服务端重新校验会话和角色，不能只依赖前端隐藏按钮。

## 7. 页面与交互实现要点

新建工单页面采用分区式的单页表单：先电话检索客户，再选择或新增设备，然后添加维修项目、确认报价、录入订金。常用字段应提供默认值、搜索和键盘友好操作，以支撑两分钟登记目标。

首页将以状态计数和可操作列表为主，而不是复杂图表；优先呈现待取机、逾期、等待确认和未结款。工单详情按“当前操作区 + 历史记录”组织，让员工可立即更新状态或收款，同时能查看报价、付款和状态历史。

## 8. 本地化、隐私与安全基线

- 首版界面文案采用可国际化资源文件，默认意大利语，并允许后续补充中文/英语。
- 仅收集完成维修所需的客户信息；电话、IMEI 等个人数据不出现在无权限的列表导出或日志中。
- 在客户档案记录隐私同意的时间和版本；完整 GDPR 流程、数据导出/删除申请作为后续需求细化。
- 密码采用安全哈希；生产环境强制 HTTPS、安全 Cookie 和环境变量管理；数据库与附件均定期备份。
- 输入在服务端用 Zod 校验，所有数据库查询通过 ORM 参数化执行；上传文件限制类型、大小并使用非可猜测对象键。

## 9. 测试与质量策略

核心领域规则用 Vitest 覆盖：报价优先级、工单金额汇总、付款余额、状态流转和权限判断。数据库集成测试使用独立测试库验证迁移、事务及审计日志。Playwright 覆盖店员从“新建客户和工单 → 自动报价 → 更新状态 → 收尾款 → 交付”的主路径，以及未结款和无匹配报价两条异常路径。

持续集成至少执行类型检查、代码风格检查、单元/集成测试、生产构建和 Playwright 冒烟测试。每次数据结构变更都必须包含 Prisma 迁移和相应测试。

## 10. 分阶段交付建议

| 阶段 | 可交付结果 |
| --- | --- |
| 基础骨架 | 登录、角色、数据库迁移、通用布局、意大利本地化基础和 CI。 |
| 核心闭环 | 客户/设备、工单、报价匹配、状态历史、付款与交付。 |
| 经营视图 | 看板、待办提醒、每日收款与基础统计。 |
| 稳定化 | 权限审计、测试补全、备份演练、性能和可用性修正。 |
| 后续增强 | 附件、签字、收据、通知、库存、税务和多门店，按产品验证结果进入。 |

## 11. 部署建议

开发环境使用 Docker Compose 启动应用和 PostgreSQL。生产环境部署一个应用容器与托管 PostgreSQL；对象存储、邮件/短信等外部服务通过环境变量接入。上线前应完成：数据库自动备份与恢复演练、错误监控、健康检查、日志保留策略，以及独立的测试与生产配置。

初期无需引入消息队列、缓存集群或搜索引擎。待出现明确证据，例如通知量大、报表查询影响日常操作或多门店数据隔离需求时，再按实际瓶颈增加相应组件。
